# Liner Code: threat model

Repository: `lynnarize/liner-code`, version 0.3.2 beta. No infrastructure repository: the app runs locally, and the marketing site is a static Cloudflare Worker defined in `site/wrangler.jsonc`.
Legend: **[user]** = stated by the repo owner; **[code]** = inferred from the code.

## System overview and trust boundaries
Liner Code is a single-user desktop agent harness (Electron, macOS and Windows). It drives the agent CLIs the user already has: Claude Code, Codex, OpenCode, Hermes, ACP agents, and OpenAI-compatible API endpoints. **[code]**

- **Electron shell ↔ renderer.** The window uses `contextIsolation`, `sandbox` and no `nodeIntegration` (`desktop/src/main.ts`). The preload (`desktop/src/preload.ts`) exposes `__LINER__` (the engine URL and token) and `linerShell.call` over one IPC channel. Popups go to `shell.openExternal` (http/https/mailto only), "Open in your editor" (`openFile`, from Changes and a Security finding) opens only a file inside the session's or project's own folder, which the shell reads from the engine rather than the page, links resolved (`desktop/src/editor.ts`), and never runs it; `openIn` (a folder in Finder, a terminal or an editor) takes the page's path, follows its links first (realpath) and judges what it resolves to, refusing a path that doesn't resolve (a dangling link, nothing there), and never opens a file as itself: a file sent to an editor goes to a known editor, else TextEdit on a Mac or Notepad on Windows (one argument, no shell), else is shown in its folder, and a file sent anywhere else is shown in its folder; on a Mac a folder whose real name has an extension (`Foo.app`, a workflow, or a link named `tools/run` that points at one) is shown in Finder whatever was asked; a plain folder is still handed to `shell.openPath`, `<webview>` is blocked, and permissions are limited to the app origin.
- **Shell ↔ engine.** The engine is a child Node process on 127.0.0.1 (`engine/src/server.ts`). `/events` and `/rpc` require `x-liner-token`, a random 24-byte per-run token compared in constant time. Secrets reach the engine on stdin and are not passed on to anything it spawns (`engine/src/main.ts`).
- **Engine ↔ local machine / other origins.** Other local apps and web pages in the user's browser can reach 127.0.0.1. Routes that skip the app token, each with its own guard:
  - `/surface`: per-session key, used by an agent's MCP tools.
  - `/outside`: key in `~/.liner-code/outside.json` (0600), only while Let apps outside Liner Code in (Settings › Liner MCP) is on. The stdio server (`outside.ts`) sends the `client` name its terminal agent gave, and each call goes through Liner MCP's gate at the level set for terminal agents (Trusted unless lowered; the file carries it as `level`, so the server lists only those tools).
  - `/hooks/r/<id>?key=`: a routine's webhook secret. Routines are switched off in this version (ROUTINES_ON in contracts/src/index.ts), so no webhook is taken.
  - `/addon-check/<token>`, `/dsh/<token>/…`: a per-run token.
  - `PANEL_FRAME`, `/health`, the static UI: no guard.
- **Liner MCP's listener ↔ apps outside Liner Code.** Only while Let apps outside Liner Code in is on, the engine opens a second listener on 127.0.0.1 (`engine/src/mcp-http.ts`; port 7318, or any free one when that is taken). It answers only POST/DELETE `/mcp` (MCP Streamable HTTP; a Bearer `lc_…` key or OAuth access token is checked before the body is read), GET `/.well-known/oauth-protected-resource/mcp`, GET `/.well-known/oauth-authorization-server`, POST `/register`, GET `/authorize` and POST `/token` (`mcp-oauth.ts`). None takes the app's token, and `/rpc`, `/events`, `/surface`, `/outside`, `/hooks` and the UI are 404 there. A request is answered only when its Host is `127.0.0.1:<port>`, `localhost:<port>` or the tunnel's public host, and an Origin, when one is sent, only when it is one of those (against DNS rebinding); the engine's own server still answers no Host but its own. A way in from the internet that the user picks (`tunnel.ts`: Tailscale Funnel, a Cloudflare quick tunnel, or an https address of their own) points at this listener and nothing else.
- **Engine ↔ agents.** Agents run with the user's sign-ins and an access mode (read/ask/edits/auto/full). `engine/src/risk.ts` classifies tool-call risk for approval cards; even in Full access, the guard asks about irreversible steps.
- **Untrusted content → agents.** Repo files, PR and issue bodies (routines), webhook bodies, and pages in the Browser surface can carry prompt injection. So can a pull request's title, description and diff, and an issue's title, description and last comments, which a scan of them quotes into its message as data (`security-targets.ts`), and the messages an app outside Liner Code starts or sends through Liner MCP.
- **Add-ons.** MCP connections (manifest only; secrets sealed in the keychain), panels in a `sandbox="allow-scripts"` iframe with a CSP and Connection-Allowlist (`contracts/src/panel.ts`, `engine/src/panels.ts`), and ported DeepSeek Harness plugins run as separate processes. Those processes are sandboxed with `sandbox-exec` on macOS and unsandboxed on Windows and Linux (`engine/src/dsh-hosts.ts`).
- **Release → user machine.** Self-update from GitHub releases checks the SHA-256 (from the release digest or a sidecar file), the bundle id, the version, `codesign --verify --deep --strict` and the same Team ID (`engine/src/updates.ts`). The shell checks the bundle id and the signature again right before it swaps the bundle in (`desktop/src/signed.ts`, `desktop/src/update.ts`); one that fails is deleted, the engine says so once, and the release downloads again.

## Entry points and who can reach them
- The engine's HTTP server on 127.0.0.1: any local process, and any web page via the browser (cross-origin requests, DNS rebinding).
- Per-port proxies of the Browser surface on 127.0.0.1 (Host and Origin checks in `proxy.ts`).
- Agent output and tool calls: driven by model output and whatever content the agent reads.
- MCP stdio servers (`mcp.ts`, `outside.ts`) started by agent tools.
- Add-on manifests and panel/plugin code written by agents or installed by the user.
- GitHub data polled by routines through `gh`, and by the once-a-minute watch (`watch.ts`) on a session's open pull request: while its saved checks read running (two hours at most from when they were first read so, kept with the session across restarts), while Settings settles sessions on merge, or while a snoozed session waits on it. The checks alone only refresh the session's pull request facts; they never settle or wake it. Webhook bodies.
- GitHub release assets fetched by the updater; npm dist-tags for tool updates.
- Commands the engine runs by itself to list a tool's models (`engine/src/providers/`). Each is a listing that runs no model turn and sends no prompt, started with the engine's environment (an OpenCode one also with Liner Code's permission rules) and only the named fields of its answer are kept, in `models.json` (a model's id, name, description, group, effort levels, default and price; never an OpenCode model's `headers` or `settings`). They run at launch when the saved list is half a day old or the tool's version changed, on Look again in Agent tools, and in Check my tools (which gives each 30 seconds). Claude Code: the Agent SDK's `supportedModels()` on a session with no prompt, in `~/.liner-code/probe` with only your user settings, 30 seconds; `claude --version`; and a second such session with the older models added to its picker for that look alone (the `modelPicker` setting), only when its answer for this account and Claude Code version isn't kept yet (`probe/claude-older.json`, the older models' rows alone). Codex: `codex debug models`, 20 seconds. Antigravity: `agy models`, 30 seconds. OpenCode: from version 2 (its `--version`, 8 seconds, read once per program file), `opencode api --standalone GET /api/model` in the probe folder (standalone, so it never starts OpenCode's background service), in a process group of its own that is ended whole past 30 seconds or when the look is stopped; before version 2, or when that fails, its ACP session as below. ACP agents (OpenCode, Hermes, Cursor, Grok Build, ones you added): `initialize` and `session/new` in the probe folder with no MCP servers, 45 seconds, then the process group is ended.
- `liner-code://` links, which any web page can open once the browser's prompt is accepted (`desktop/src/deeplink.ts`): one naming a session opens it; one naming a folder (`open?path=`) asks in a native dialog before the folder is added as a project, since adding one runs git there. A folder named on a command line you typed is added without asking.
- OpenCode's local server: the engine starts `opencode serve` on 127.0.0.1 and drives it over HTTP and server-sent events (`providers/opencode-server.ts`), one process shared by the sessions on that binary and configuration; its permission requests come back to Liner Code's access levels as the ACP driver's do, a command judged whole and not by its first part. Its password is made each start and handed to it as OPENCODE_PASSWORD in its stdio mode, which takes it out of its own environment before it starts anything, so the commands agents run don't carry it; it is still in that server process's own environment, which anything running as you can read (`ps -E`), as with OpenCode's own ACP server. Each session's commands get that session's environment (`PUT /api/session/:id/environment`), never a password. Your own opencode.json denies stay in force, and a server that doesn't answer a Stop for 15 seconds, nor a check after it, is ended with all it started.
- A project's `.liner/patch.json` (`patches.ts`), which comes with the repository: it may add `deny` and `ask` permission rules and change presets, never `allow` rules (those only from `<LINER_HOME>/patch.json` or Settings).
- Outbound, on a press or a keystroke: `gh pr list` when you type `#` in the message box (cached 30 seconds), and `git fetch` and `git pull` from Fetch & pull.
- Liner MCP's listener (above): any local process or web page while it is on, and anyone on the internet who has the tunnel's address while one is up. Every call, by either door, goes through one gate (`mcp-apps.ts` `McpGate`) that checks the app is still let in, its rate (60 calls a minute) and its level: Read only lists and reads projects, sessions, pull requests, issues and findings; Asks first adds starting, messaging, waiting on, answering a session's question, scanning and stopping, and each start, send, answer, scan or stop waits up to 10 minutes for Allow on a card in the app (its sessions run at Manual), so only `liner_wait` and the read tools run without one; Trusted does all of it without a card, its sessions at the user's default access but never Full access (Edits instead). A message or an answer to a session already at Full access asks at any level. No tool answers a permission ask or changes a setting. Keys are `lc_` and 32 random bytes, shown once, kept as SHA-256 in `<LINER_HOME>/mcp-apps.json` (0600) and compared in constant time, good for 30 days and revoked at once (open calls end with it). OAuth: dynamic registration with the client's name and redirects HMAC-signed into its id (nothing stored), https or loopback redirects only, PKCE S256 only, the code exchanged only with the very redirect_uri `/authorize` was given, and the sign-in completes only after the user allows it on a card in the app and picks its level (five waiting at most). `/authorize` makes that card only within 15 minutes of the user picking Claude, ChatGPT or Another app in Add an app (`mcp.expectSignIn`); otherwise it shows a page that says to start from Liner Code. The card names the redirect's host and says what the app calls itself, never with a logo taken from that name. `/authorize` makes at most 10 cards a minute, counting only calls that would make one (past it, a page says to wait), and allowing a sign-in closes its 15-minute window; `/register` takes at most 300 registrations a minute, counting only those that succeed (429 past it); the code is good once for a minute, an access token for an hour, and a refresh token is used up as it's used. Each call is logged as `[mcp] <app> <tool> <outcome>`, never with its words or key. A terminal agent has no key of its own: revoking one turns it away by the name it gives (listed as Turned away, Let in again through `mcp.unblock`); with Let apps outside Liner Code in off, `outside.json` and its key are gone, so none gets in, and turning it on again lets the turned-away names back in.
- Processes the engine starts for a way in from the internet, only when the user picks that way: `tailscale status --json` (for the tailnet name), `tailscale funnel status --json` (Funnel already serving something else on :443 is left alone), `tailscale funnel --bg <port>`, `tailscale version`, and `tailscale funnel --https=443 off` when it stops or the engine quits; or `cloudflared --version` and `cloudflared tunnel --no-autoupdate --url http://127.0.0.1:<port>`, a trycloudflare.com address new each start, ended with the engine (if it gives no address in 30 seconds, `tailscale status --json` is read for an exit node). Each tool's command runs in a process group of its own, killed whole at its time limit. While a way is up the engine sends one GET to its own public address, `/.well-known/oauth-protected-resource/mcp`, when it comes up, every 5 minutes and on Check again, to see that it reaches the listener; nothing goes anywhere else. "Your own address" starts nothing; it is only the https address apps are given.
- Outbound, Tell an app (`mcp-webhook.ts`): when a session (not a side one) turns to waiting and an address is set, one POST of `{"event":"needs_you","session":<its title>,"app":"Liner Code"}` with the `mcp.webhook` secret from the keychain as a Bearer token if there is one; https only, no user or password in the address, never to this computer or a private network (loopback, 10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10, fc00::/7, fe80::/10, localhost names: refused when saved, and the name is looked up again at each try, as for AI pictures' links, `ip.ts`), no redirects, 10 seconds, two retries. It does not depend on the Let apps in switch.
- Outbound, pull requests and issues (`worklists.ts`): `gh pr list`, `gh pr view`, `gh issue list`, `gh issue view`, `gh api user` and `gh auth status` in each GitHub project's folder for the Pull requests and Issues pages (and for apps through Liner MCP), each list kept for `worklistRefresh` seconds (120 by default); `git remote get-url origin` for a project with no remote kept. Once Pull requests has been opened on this Mac, the sidebar asks for the open list itself, 5 seconds after a window comes up and then every `worklistRefresh` seconds (60 at the least; 0 turns it off) while the window is visible. Linear: POST https://api.linear.app/graphql with the key as Authorization, no redirects, when the key is added (to check it) and when Linear's issues are listed or opened while its switch is on. The Bitbucket app password is kept (`scm.bitbucket`) and sent nowhere in this version. Settings › Source control & issues asks each tool for its version and its own sign-in status (`git`, `gh`, `glab`, `az`, `fj` or `tea`, `origin`), and keeps only names.
- Scans of a pull request or an issue (`security-targets.ts`): a read-only Liner Security session of the user's own tool (sealed when a Specialist runs it; a Linear issue is refused for now, having no folder to read), 15 minutes for a pull request and 10 for an issue, the target's text quoted as data. It reads through `gh pr view`, `gh pr diff` or `gh issue view`, and runs `git fetch --no-tags --no-write-fetch-head origin pull/<n>/head` only when the head commit isn't local (objects only: no ref, no checkout), reading files with `git show <head>:<path>` so the working copy is never touched. `gh pr comment` or `gh issue comment` with `--body-file -` runs only on the user's second press of Comment, and posts the scan's sentence and its findings' titles and files, nothing of the code. Scan new PRs (`security-watch.ts`, `scanNewPrs`, off by default) is a 60-second engine timer that looks at most every five minutes (or `worklistRefresh`, if longer) while a window reads `/events`, asks `gh pr view --json headRefOid` for at most 50 changed pull requests a look, and starts one scan at a time, never of a draft, at most 10 a day (a pull request whose scan fails to start twice at one head commit rests an hour, and after four waits for a new commit); it keeps each pull request's key and head commit and the day's count in `<LINER_HOME>/security/watch.json`.
- Outbound: one anonymous usage count a day to linercode.dev (engine/src/usage-ping.ts): install id, version, OS and chip, day, token counts. Off with the Settings switch or LINER_NO_USAGE=1.

## Assets
All of the following are equally critical **[user]**:
- API keys and agent sign-ins (safeStorage in `desktop/src/keys.ts`, the keychain, add-on secrets).
- Source code and git history in the user's projects, including `refs/liner/` checkpoints and worktrees.
- Code execution on the user's machine.
- Routines that act on GitHub: merge, comment, label, close.
- The engine token, the surface/outside keys and webhook secrets, which guard the above.
- Liner MCP's app keys, OAuth tokens and the HMAC secret its client ids are signed with (`mcp-apps.json`), which let an app start and message sessions; the Linear key, the Bitbucket app password and Tell an app's secret (keychain `scm.linear`, `scm.bitbucket`, `mcp.webhook`).

## Attacker profiles
All of the following matter **[user]**:
1. A malicious web page or another local app reaching the engine, a proxy or a plugin port on 127.0.0.1.
2. Untrusted repo content, PR or issue text, webhook payloads or web pages that steer agents through prompt injection.
3. A malicious add-on, panel or DeepSeek Harness plugin, including one an agent drafted.
4. A tampered update or a compromised release supply chain.

No multi-user, server-side or cloud attacker: the app has no backend of its own **[code]**. The exception is a way in from the internet the user turns on for Liner MCP: while it is up, anyone who learns the tunnel's address can reach Liner MCP's listener (not the engine's), and still needs an app's key or a sign-in the user allowed **[code]**.

## Existing controls
**[code]**
- The per-run token is required on `/rpc` and `/events`, compared with `timingSafeEqual`, and the server binds to loopback only.
- Each sensitive route has its own scoped secret; webhook secrets are compared in constant time (`routines.ts`).
- The Electron window is hardened: sandbox, context isolation, permission handler, `<webview>` blocked, external links allowlisted by scheme.
- Panels get a sandboxed iframe with an opaque origin, a CSP, a Connection-Allowlist against WebRTC, and an engine-side access check (`panels.ts` `refusal`). The Connection-Allowlist header fails open: if an Electron upgrade stops honouring it, nothing blocks WebRTC from a panel, so desktop/test/panel-network.test.ts must pass (not skip) after every Electron upgrade.
- The proxy checks that Host is 127.0.0.1/localhost on its own port, against DNS rebinding.
- DSH plugins run under `sandbox-exec` on macOS (no access to keys or Liner state); there is no sandbox on Windows or Linux, and the plugin's card says so.
- Updates are checked by SHA-256, bundle id, version, codesign and the same Team ID. The Team ID check applies only once this copy is signed with a Developer ID; an ad-hoc copy takes the first signed release and is pinned from then on. The SHA-256 comes from the same release as the download, so it proves the download is whole, not who published it.
- `risk.ts` marks destructive commands as high risk, and Full access still asks about irreversible steps.
- Hermes's agents sent to the background: the engine reads the live log Hermes writes for each one, only a `task-<n>.log` that resolves (links followed) under that Hermes's own `cache/delegation/live`, whatever path its dispatch names, and only its last megabyte, every 0.7 s while it grows, for six hours at most (`acp.ts` `liveLogs`, `follow`). It reads nothing else of Hermes's home and writes nothing there.
- Routine gates are code, not AI: merges are limited per day and pinned to the commit that was read.
- Liner MCP: a listener of its own that serves nothing of the app, Host and Origin checks, keys and tokens kept only as hashes, a level held in the engine on every call whatever the app was shown, no tool for permission asks or settings, never Full access for an app's sessions, Allow cards at Asks first, 60 calls a minute, 30-day keys, and nothing on the internet unless the user picks a way in.

## Out of scope / accepted risk
- `site/` (the marketing website) **[user]**.

## Open questions
- Windows does not update itself yet: a packaged Windows copy only tells you a new version exists (engine/src/updates.ts). When it gains an updater it needs integrity checks equal to codesign and Team ID.
- Is remote access or a public webhook ingress planned? It would widen the routines and engine surface. Liner MCP's tunnel is the first remote access: it reaches only Liner MCP's listener, so an app's key or sign-in, and its level, is all that stands between the internet and starting a session.
