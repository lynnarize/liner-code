# Edge cases from T3 Code's tests

T3 Code drives the same tools as Liner Code, and its tests record what went wrong for its users.
This goes through 874 of its test names (Claude Code, Codex, ACP agents, the turn loop, history),
at T3's `337c5858c` (2026-11-05), and checks each one that applies against Liner's engine. Of those,
421 merged into the 175 cases here; the rest were T3-only features or plumbing.

Five audits read the code and the tests. Nothing was run, except where a note says so, and nothing
in the code was changed. The five gaps in "Fix first" were then checked by hand against the code, and fixed.
The other gaps come from the audits alone, so read the code before fixing one: an audit can be
wrong. Line numbers are from 2026-11-06, commit `2616202`.

- **High**: lost work, wrong permissions, or a session that sticks.
- **Medium**: a wrong state shown, or a failure you can recover from.
- **Low**: cosmetic.

## Fix first

All five fixed on 2026-11-06, each with a test that failed first, and checked with fake agents in
the engine's tests, not with the real tools. The line numbers in the table above and below don't
include these changes. The tally still counts them.

- [x] **A read-only turn on Claude Code could run a write command.** A lead's plan and a side chat
  were read-only only because the edit tools were denied, and the approval hook read the thread's
  access rather than the turn's. Now, in a planner's turn, a side chat or Read only, a command that
  isn't read-only or an edit never goes ahead by itself: no earlier "don't ask again", no Auto, no
  Reviewer. It comes to you as a card, and in a routine or a cost test it's declined
  (`engine/src/runtime.ts`, `approve`). T3: `ClaudeAdapterV2.test.ts:396`, `:4571`, `:4623`.
- [x] **An ACP agent's edits were approved wherever they pointed.** In Edits, Auto and Reviewer
  decides, an edit now goes by itself only when every file it names is in the project. One outside,
  or one that names no file, comes to you as a high-risk card that "don't ask again" can't cover
  (`engine/src/providers/acp.ts`). Full access is unchanged. T3: `clientPolicy.test.ts:47`, `:71`.
- [x] **A symlink took an ACP agent out of the project.** `inProject` now follows links, and a link
  to nothing counts as outside, since a write would follow it (`engine/src/providers/acp.ts`,
  `realPath`, after T3's `clientPolicy.ts`). A file named `..notes` no longer counts as outside.
- [x] **"Ask first" didn't ask on `codex exec`.** It can't stop to ask, so Ask first and Reviewer
  decides now run read-only there, and say so once in the session
  (`engine/src/providers/codex.ts`). `supports.approvals` is still unread.
- [x] **Two tools out of usage handed a session back and forth with no end.** The runtime now keeps
  when each tool has usage again, and `fallbackFor` skips one that's out, so a session makes one hop
  and stops on the limit card (`engine/src/runtime.ts`). A tool that doesn't say when counts as out
  for an hour.

Two more gaps the audits rated high are medium below, because they're real but rare: a failed disk
write at the end of a turn leaves it running, and a message sent during a rewind's undo starts a turn
the rewind then cuts off.

## Other gaps

The ones ticked here were fixed on 2026-11-06, each with a test that failed first, and checked with
fake agents and fake tools, not the real ones. Their text is as the audit found them. The tally still
counts them. The worktree part of the Stop gap covers a new worktree and one being put back. A gap
left open with "Partly fixed" says what's still missing.

### Turn loop

Liner paths are under `engine/`.

- [x] **Medium.** A failed disk write (disk full, folder read-only) while a turn ends leaves the turn registered as running forever. `sink.end()` settles the streaming item with a logged write, which throws, so the next line `this.turns.delete(threadId)` never runs. `isRunning` then stays true and every later message just queues; nothing drains it until the engine restarts. (src/runtime.ts:825-830 (`sink.end()` is the first line of `finally`), src/runtime.ts:1752-1757 (settle), src/store.ts:399 (appendFileSync in putItem); T3: ProviderEventIngestor.test.ts:2350 (a failed event write fails the run cleanly); UserFacingErrors.test.ts:39 (full database, retry after capacity returns)) Found by reading, not run. The same failure inside the `catch` (line 819, `sink.api.error` calls putItem) also escapes. main.ts:155 keeps the process alive, so the thread looks hung rather than the engine crashing. No test injects a write failure. Rated high in the audit, lowered on checking: real, but rare.
- [x] **Medium.** Quitting the app while the agent has an open question marks the question expired instead of keeping it. `shutdown()` aborts every turn, the abort handler of `wait()` writes the card as expired (synchronously, to the log) before `process.exit`. After restart the question is gone, and the turn is not continued because an expired card blocks the continuation. The design says an open question outlives its turn and its answer goes as the next message. (src/runtime.ts:1568-1574 (gone() expires "asking" items, questions too), 1510 (shutdown calls stop), src/main.ts:145, src/runtime.ts:1471 (expired card skips continuation); T3: ProviderRuntimeRecoveryService.test.ts:85 (preserves async questions across startup and shutdown); ProviderSessionManager.test.ts:3177 (questions preserved only for server shutdown)) turns.test.ts:276 only builds a Store from disk; it never goes through shutdown(), so it misses this.
- [x] **Medium.** Pressing Stop while a message is waiting for a new worktree to be set up (up to 15 minutes) does nothing. The message starts anyway once setup ends. (src/api.ts:970-972 (thread.stop only calls runtime.stop), src/api.ts:933-939 (send waits on `setups`), src/runtime.ts:1229-1233 (stop needs busy or a turn); T3: SteeringCompletion.integration.test.ts:1720 (stops a turn that is still starting)) `working()` (api.ts:302) counts setups for undo and rewind, but stop doesn't. Same for a worktree being recreated (ensureWorktree).
- [x] **Medium.** A `/goal ...` sent while a turn runs is queued as plain words. When the queue drains it is joined with other messages and sent to the agent as text, so no goal starts. `/reviewer` sent while busy behaves the same. The goal and reviewer commands are only read in the idle path. (src/api.ts:915-931 (goal only when stop-word or not running), src/runtime.ts:210-225 (drain sends joined text through `send`, no command check); T3: SteeringCompletion.integration.test.ts:1596 (promotes a queued goal); :1552 (a goal sent into a running turn goes next)) The `/goal stop` word is handled immediately even while running (api.ts:918), which is fine.
- [x] **Medium.** Answering the same question twice sends the answer twice. `answerQuestion` never checks that the card is still asking. The second call finds no waiter and an answers object, so it starts or queues another message with the same text, and overwrites the card. A double click or a second window does it. (src/runtime.ts:1264-1276 (no state check; `else if (answers) void this.send(...)`); T3: RuntimeRequestService.test.ts:18 (responds only to resolved requests); ProviderEventIngestor.test.ts:1301) `answerProposal` has the guard (line 1281), and `answer` throws for a missing waiter (1255), so only questions are open to this.
- [x] **Medium.** When a message can't start before its turn begins (a worktree that can't be recreated, an attachment that can't be saved), the message is dropped. The only trace is a toast. It isn't on the timeline or in the queue, so the typed text is lost.
